# Testing — layoffs-tracker

How tests are written, named, run, and reported here. If you are an agent, read
this before writing a test — the naming rules are load-bearing, not style.

## 1. The contract: red before green

A task is not started by writing code. It is started by writing a test that
fails for the right reason.

1. **RED** — write the test. Run it. Watch it fail. A test that has never failed
   has never been shown to test anything.
2. **GREEN** — write the least code that passes it.
3. **REFACTOR** — clean up with the test still green.

The failure in step 1 must be an assertion failure, not an `ImportError` or a
typo. "It errored, close enough" is how a permanently-passing test gets written.

**A task cannot be marked done while its test is red.** Onigiri enforces this at
the Done gate (`oni set KEY --status done` refuses). `--force` exists, requires a
reason, and shows up in the digest — use it for a genuinely untestable task, not
for a test you have not gotten around to fixing.

## 2. Test targets: one test, proved by the JUnit report

Onigiri stores a **target** on a task — the node id of the single test that
proves it. Not a suite, not a file. `.onigiri.toml`'s `test` command takes two
placeholders: `{target}` (the node id, substituted as a bare argv element) and
`{report}` (a JUnit XML path Onigiri generates for the run).

### Why a report, not the exit code

`go test -run`, `jest -t`, and `cargo test` all exit 0 when `{target}` matches
*zero* tests — a typo'd or stale target runs nothing and still reports
success. Verified transcripts:

```
$ go test -run 'TestDoesNotExist' -v ./...
testing: warning: no tests to run
PASS
ok  	goprobe	0.159s [no tests to run]
$ echo $?
0
```

```
$ npx jest -t "this pattern matches nothing at all xyz"
Test Suites: 1 skipped, 0 of 1 total
Tests:       2 skipped, 2 total
$ echo $?
0
```

```
$ cargo test doesnotexistzzz
running 0 tests
test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 2 filtered out
$ echo $?
0
```

A green exit code here proves nothing ran, not that something passed. So
Onigiri never trusts it: after the run, it reads `{report}` and looks for
`{target}`'s node id as a `<testcase>` element. Pass if that testcase passed;
fail otherwise — including "not present in the report at all", which is
exactly the zero-match case above.

### Node ids and what actually runs

| Runner | Runs in | Node id looks like | `test` command |
|---|---|---|---|
| pytest | repo root (python) · `backend/` (web-api) | `tests/test_core.py::test_greet_trims_name` | `uv run pytest --junitxml={report} -- {target}` |
| vitest | `frontend/` (web-api) | `src/lib/greet.test.ts::trims surrounding whitespace` | `npx --no vitest run <file> --reporter=junit --outputFile={report}` |

pytest runs exactly the node id (plus any parametrized variants); vitest runs
every test in the target's file. That over-matching used to be a
correctness bug — a task's evidence contaminated by a sibling test's outcome.
It isn't one anymore: Onigiri reads only the `<testcase>` in the report whose
node id is `{target}` and ignores everything else the run happened to touch.
What over-matching still costs is wall-clock time, not verdict correctness.

### web-api: two runners, one command

`.onigiri.toml` holds one `test` command, and web-api has two runners.
`scripts/oni_cmd.py` routes each target by its file extension: `.py` goes to
pytest in `backend/`, `.ts`/`.tsx` to vitest in `frontend/`.

- **Write targets relative to their side:** `tests/test_main.py::test_health_returns_ok`,
  not `backend/tests/…`. The JUnit report names each test relative to where its
  runner ran, so a `backend/` prefix never matches.
- **vitest targets must be top-level tests.** A test inside `describe("x", …)`
  is reported as `x > name`, and Onigiri rejects `>` in a target. Keep any test
  you will target at the top level of its file.
- **`collect` reads `vitest list --json`, not its exit code.** `vitest list`
  exits 0 even for a file that does not exist.

Consequences that remain:

- **Renaming a test breaks its target.** The target is a string, not a
  reference. Rename deliberately and update the task (`oni set KEY
  --test-target …`).
- **Targets are validated at write time** by the `collect` command in
  `.onigiri.toml` (both profiles define one), so a typo fails while you are
  still looking at it.
- **A target is never a shell string.** It is substituted as one argv element
  and never re-split. `; rm -rf /` in a target is an inert argument, and is also
  rejected at write time. Do not try to smuggle flags through it.

## 3. CI must upload `junit.xml`

This is a second, separate JUnit report from the `{report}` one in section 2.
`{report}` is per-run and per-target, generated by Onigiri for a single `oni`
invocation. `junit.xml` here is whole-suite: CI runs `scripts/check.sh`, which
runs every test with a JUnit reporter, then uploads the result as an artifact
named `junit`, with `if: always()`, for `oni sync-ci` to download after CI runs.

This is not optional plumbing. JUnit XML is **per-test**: it carries one
`<testcase>` element per node id with its own outcome. `oni sync-ci` downloads
it and updates the individual tasks whose targets match. Without it, the only
signal CI gives is one exit code for the whole run, which can mark a project
green or red but can never tell you *which card* to move.

`if: always()` matters for the same reason — a failing run is precisely the run
whose per-test breakdown you want. Skipping the upload on failure discards the
only useful half.

Emitting it: pytest `--junitxml=junit.xml` · vitest
`--reporter=junit --outputFile.junit=junit.xml`. web-api uploads
`backend/junit.xml` and `frontend/junit.xml` in the one `junit` artifact;
`oni sync-ci` reads every `.xml` inside it.

## 4. Fixture patterns

Three patterns cover almost every "this test is slow / flaky / needs the
network" problem. All three are the same move: **the thing that varies is passed
in, not reached for.**

**Injected clock.** Never call `Date.now()` / `datetime.now()` inside logic under
test. Take a clock as a parameter, defaulting to the real one; pass a frozen one
in tests. This kills every "fails at midnight", "fails in CI's timezone", and
`sleep()`-in-a-test problem at once, and it makes "was this due yesterday?"
testable without waiting a day.

**Injected subprocess runner.** Same shape, for anything that shells out or hits
the network. The unit under test takes a `run(argv) -> result` callable; tests
pass a fake that records the argv it was handed and returns a canned result.
Asserting on the recorded argv is how you test that a command was *built*
correctly without executing it — which is the only sane way to test a code path
whose real effect is `rm`.

**Temp-dir isolation.** Any test that touches the filesystem gets its own temp
directory, created and torn down by the test framework, and never writes to the
repo or to `~`. A test that leaves files behind passes alone and fails in a full
run, or worse, passes only because a previous test left something behind.

The rule underneath all three: **a test must pass on a machine with no network,
no models installed, an empty home directory, and a wrong system clock.** If it
cannot, it is an integration test — label it and keep it out of the fast loop.

## 5. Coverage bar

**80% line coverage, floor not target.** CI enforces it: `pytest
--cov-fail-under=80`, and in web-api also vitest's `coverage.thresholds.lines:
80`. A PR that drops coverage below the floor fails.

Coverage measures which lines ran, not whether anything was asserted, so treat
it as a smoke detector: 100% coverage with no assertions is worthless, and the
last 15% is usually error paths that are worth more than the happy path already
covered. Chase the uncovered `except` / `catch` branches before chasing the
number.

Every non-obvious invariant gets its own test, named after the invariant rather
than the function — `rejects_target_escaping_repo_root` tells you what broke;
`test_validate_2` does not.
